The Problem: Transactional Race Conditions

Concurrent read-modify-write operations on un-synchronized resources lead to "Lost Updates".

t=0mst=50mst=100mst=150mst=200ms
T1: READ (Seats=1)
T1: WRITE (Seats=0)
T2: READ (Seats=1)
T2: WRITE (Seats=0)
⚠ RESULT: Two students allocated to one seat (Overbooking)
  • Lost Update Phenomenon: Occurs when concurrent transactions read identical state, leading to overwriting of allocation counts.
  • Integrity Breach: Without synchronization, the database fails to enforce the physical limit of available resources.

When T1 and T2 read the same state simultaneously, T2's write overwrites T1's, effectively "losing" an update and breaking data integrity.

Barging & Fairness Violation

Optimistic locking with retries destroys the "First-Come-First-Serve" requirement.

S1 (Clicks @ t=0)
Collides & Retries
➔
S2 (Clicks @ t=50)
Succeeds on 1st try
➔
S1 (Retry @ t=100)
Slot Full!
"FCFS fairness violated: Later arrivals overtake earlier ones"
  • The Barging Problem: Later requests can acquire locks while earlier requests are in a "back-off" or retry state.
  • Fairness Guarantee: Strict FCFS ensures that temporal priority is the only factor in resource acquisition.

"Barging" occurs when a late-comer acquires a lock while an earlier request is in a "back-off" period following a collision.

Design Objectives

FCFS Fairness

Requests that arrive earlier must be served before later ones — no thread barging allowed.

Deadlock Freedom

Concurrent transactions must never stall each other in circular lock waits.

Atomicity

A student is enrolled in all courses within a slot, or none — no partial allocations possible.

These objectives ensure that the system is both concurrency-safe and operationally reliable.

Formal Algorithm: Concurrency-Safe FCFS Allocation

Goal: Guarantee Atomic Slot Allocation and Zero Overbooking under High Contention. Input: student_id, slot_id Output: Success or Exception Step 1: The Wait-Free Doorway (Discovery) 1. START TRANSACTION (Spring @Transactional) 2. FETCH all tcaid (Primary Keys) from ec2.termcourseavailablefor where the slot matches. 3. VALIDATE student eligibility: * Check ec2.studentregistrations to ensure student exists. * IF student already has records in ec2.studentregistrationcourses THEN ROLLBACK & THROW AlreadyEnrolledException. Step 2: Resource Serialization (The Growing Phase) 4. SORT the list of tcaid in ascending order. * Mechanism: Prevents AB-BA Deadlocks. 5. ACQUIRE PESSIMISTIC LOCKS: * FOR EACH tcaid in the sorted list: * Execute: SELECT * FROM ec2.termcourseavailablefor WHERE tcaid = ? FOR NO KEY UPDATE * Result: Parallel threads requesting the same courses are serialized into a FIFO queue. Step 3: Atomic Consistency Check & Commit 6. VERIFY CAPACITY: * FOR EACH locked row in ec2.termcourseavailablefor: * IF tca_booked >= tca_seats THEN ROLLBACK & THROW RuntimeException("Slot Full"). 7. EXECUTE PERSISTENCE: * UPDATE tca_booked = tca_booked + 1 in ec2.termcourseavailablefor. * INSERT student-subject mapping into ec2.studentregistrationcourses. 8. COMMIT TRANSACTION * Result: All locks are released; seats are officially allocated.

Phase 0: The Wait-Free Doorway (Discovery)

Filename: AllocationService.java

// 1. Fetch identifiers only (Bypasses Hibernate L1 Cache) List<Long> tcaIdsToLock = termCourseAvailableForRepository.findTcaIdsBySlot(slotId); if (tcaIdsToLock.isEmpty()) { throw new SlotNotFoundException(slot); } // 2. Validate Student Eligibility StudentRegistration registration = studentRegistrationRepository.findFirstBySrgstdidOrderBySrgidDesc(studentId); if (registration == null) { throw new RuntimeException("Student registration record not found"); } // 3. FCFS Pre-check: Only 1 slot per student long existingRegistrations = studentRegistrationCoursesRepository.countBySrcsrgid(registration.getSrgid()); if (existingRegistrations > 0) { throw new AlreadyEnrolledException(); }

Strategy: Discovery phase is wait-free. We identify the target rows without blocking other students, ensuring system responsiveness during the initial request handling.

Phase 1: Growing Phase (Acquiring Locks)

Filename: AllocationService.java

// 1. Two-Phase Locking (2PL): Sort to prevent deadlock Collections.sort(tcaIdsToLock); // 2. Acquire Pessimistic Locks (FOR NO KEY UPDATE) List<TermCourseAvailableFor> lockedTcafs = new ArrayList<>(); for (Long tcaid : tcaIdsToLock) { // This executes the database-level lock and queueing TermCourseAvailableFor lockedTca = termCourseAvailableForRepository.findTcafByIdWithLock(tcaid); lockedTcafs.add(lockedTca); }

Strategy: Serialization. By sorting IDs and using FOR NO KEY UPDATE, we force concurrent requests for the same subjects into a strict FIFO queue in the database kernel.

Phase 2: Atomic Commitment (Persistence)

Filename: AllocationService.java

// 1. Final Capacity Check (Safe after locking) for (TermCourseAvailableFor lockedTca : lockedTcafs) { if (lockedTca.getTcaBooked() >= lockedTca.getTcaSeats()) { throw new RuntimeException("Slot Full: No seats remaining for subject..."); } } // 2. Atomic Update & Enrollment for (TermCourseAvailableFor lockedTca : lockedTcafs) { lockedTca.setTcaBooked(lockedTca.getTcaBooked() + 1); termCourseAvailableForRepository.save(lockedTca); StudentRegistrationCourses enrollment = new StudentRegistrationCourses(); enrollment.setSrcsrgid(srgid); enrollment.setSrctcrid(lockedTca.getTermCourse().getTcrid()); studentRegistrationCoursesRepository.save(enrollment); }

The entire method is @Transactional. If any part of Phase 2 fails (e.g. seat full), the database rolls back all changes, ensuring 100% data integrity.

  • Atomic Commitment: Guarantees all-or-nothing allocation for the entire slot.
  • Auto-Rollback: Any runtime exception triggers an instant database revert of booked counts.

Concurrency: Holder vs. Waiters

Transaction A
LOCK HOLDER
Status: Executing logic
Transaction B
WAITING
Status: Blocked @ SELECT FOR UPDATE
Transaction C
WAITING
Status: Blocked @ SELECT FOR UPDATE

Threads B and C wait in the database kernel queue until Transaction A commits, effectively serializing the thundering herd.

  • FIFO Queueing: PostgreSQL manages the wait-order based on transaction arrival time.
  • Lock Persistence: The FOR NO KEY UPDATE lock is held until the final COMMIT.

Deadlock Prevention: Global Ordering

X Circular Wait (Risk)

T1 locks A, waits for B.
T2 locks B, waits for A.
→ DEADLOCK

✓ Global Ordering (Fix)

Everyone sorts: A < B
T1 locks A, then B.
T2 waits for A.
→ SAFE

No thread can hold a higher ID and wait for a lower one, making deadlock structurally impossible.

  • Global Lock Ordering: Sorting resource IDs (TCA_IDs) eliminates the "Circular Wait" condition.
  • Structural Prevention: Ensures deterministic acquisition order, removing the need for costly deadlock detection.

Other Key Decisions

ddl-auto=validate

Refuses to start on schema mismatch — protected shared tables from silent corruption during iterative dev.

termid=78 hardcoded

Scopes all queries to the active academic term — prevents stale-term allocations.

HikariCP max 20

Caps the connection pool; beyond this, threads queue for connections before even reaching row-lock queue.

These configuration choices ensure system stability and predictable behavior during deployment.
